# Technical Debt (as audited, 2026-10-03)

Each item says where the problem is, why it matters for the framework goals, and
what is planned. Severity is about the risk to **correctness or extensibility**,
not effort. Status is updated as items are paid down.

| # | Item | Where | Severity | Status |
|---|---|---|---|---|
| D1 | Workloads carry **no input data**: every task body generates its own operands (`i+1`, `i+2`). Real application data cannot be expressed at all | `scheduler/runtime/gen_dynamic_scheduler_demo.py` bodies, `codegen.reference` | **High** (blocks every adapter) | Open: Phase 3 |
| D2 | Generated accelerator code **never checks STATUS.ERR**. An out-of-range LEN makes the hardware skip the op, and the program copies stale VECOUT as if it were the result | accelerator bodies | **High** (silent wrong result if a bad size reaches codegen) | Open: guarded today only because sizes come from fixed lists; the Phase 5 runtime must reject sizes before codegen and the backend should check ERR |
| D3 | The co-scheduler imports its task bodies from a Phase 15 demo script via `sys.path` manipulation. The operation set is spread over three places: `CPU_BODY`, `ACCEL_BODY`, `reference` | `codegen.py` imports | Medium | Partly paid (Phase 2): `scheduler/framework/operations.py` is the one registry and the only importer of the bodies; the bodies themselves stay in the Phase 15 script, which Phases 15/16 still use |
| D4 | `run.py` is a monolith: profiling, planning, codegen, simulator invocation, output parsing, verification, reporting and scoring in one file | `scheduler/coschedule/run.py` | Medium | Paid (Phase 2): split into `scheduler/framework/` modules; `run.py` only orchestrates |
| D5 | The RTL file list is duplicated (Python list in `run.py`, also in the Makefile and other scripts) | `run.py`, `Makefile` | Low | Partly paid (Phase 2): one Python definition (`framework/simulator.py`); the Makefile and older collectors keep their own lists |
| D6 | Task identity is `(op, n)`, so two tasks with the same op and size are indistinguishable, and there are no dependencies, ids, or metadata | `codegen.STREAMS`, `planner` | Medium | Phase 3 (IR) |
| D7 | Cost model = exact-size lookup; an unprofiled size has no cost (KeyError), and there is no notion of measured vs. interpolated vs. extrapolated | `planner.plan_cost` | Medium | Phase 6 |
| D8 | CPU multiply (`mul32`, shift-and-add) has **data-dependent latency**: loop count = bit length of the multiplier (32 iterations for any negative value). All profiles use small positive synthetic operands, so CPU dot/matmul costs are **optimistic for real data** | `MUL32` | **High** for adapters with real data | Open: Phase 6 must profile with representative data |
| D9 | Matmul CPU/accelerator bodies require N to be a power of two (index by shift) and N <= 8; vectors N <= 64. The limits come from body code + `MAX_DIM`, not from a declared capability | bodies, `accelerator.sv` params | Medium | Phase 4: backend capability declarations |
| D10 | Fixed memory layout: CPU scratch at RAM `0x1000`/`0x2000`, outputs packed from `0x3000` with a 1,024-word ceiling. RAM addresses beyond the instantiated depth **alias silently** | `codegen.layout`, `dmem.sv` | Medium | Phase 3/5: layout allocator with explicit bounds checks |
| D11 | Register convention is implicit: bodies clobber x1..x27; the window protocol restores only x1. Correct today (the WAIT half re-derives everything else), but nothing enforces it | `codegen.program` | Medium | Phase 4: documented + checked in the backend |
| D12 | The start/collect split is found by **text search** for `"{tag}_wait_loop:"` | `codegen.accel_split` | Low (asserted, fails loudly) | Phase 4: bodies emitted as explicit launch/collect parts |
| D13 | No Python unit tests; all checks are full simulations (`make demo`: 6 min 40 s measured on this container) | repo-wide | Medium | Paid (Phase 2): `make test_framework`, 22 tests in about 5 s, incl. a byte-identical golden check |
| D14 | Plan cost model assumes exactly one accelerator; a window host cannot host another accelerator task | `planner` | Low (true to hardware) | Phase 9 design item |
| D15 | Simulator invocation and output parsing (regexes over `$display` text) are inline per script | `run.py` and older collectors | Low | Paid for the co-scheduler (Phase 2): `framework/simulator.py`; older phase scripts unchanged |
| D16 | Results are written by several generators with "Generated <timestamp>" lines, so a full regression dirties files that did not change in substance | `scripts/run_*.py` | Low | Noted; the regression check ignores timestamp-only diffs |
| D17 | Numeric semantics (mod 2^32, low-word product) are documented only in the RTL header; no software-visible capability says so | `accelerator.sv` | Medium | Phase 4/8: `NUMERICAL_REPRESENTATION.md` + backend metadata |

Left as-is in Phase 2 so the programs stay byte-identical to the baseline | `rv32_codegen.program` | Low | Fix with the next intentional program change, re-baselining the hashes |

## Not debt (deliberate, keep)

- One accelerator, one operation at a time, no DMA: these are the hardware's actual
  properties. A DMA engine is a separate hardware phase (see roadmap), not a
  software refactor.
- Offline (ahead-of-time) plans: the measured result is that on-CPU runtime decision
  cost is the binding constraint here (`docs/scheduler_v2.md`), so static plans are the
  right default.
