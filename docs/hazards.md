# Pipeline Hazards (Phase 6)

This document covers the three hazard types Phase 6 adds handling for to
the pipeline built in Phase 5 (`rtl/cpu/riscv_cpu_pipeline.sv`): data
hazards (forwarding), the load-use hazard (stalling), and control
hazards (branch/jump flush). See `docs/pipeline.md` for the pipeline's
overall structure and register contents, which this document assumes.

## 1. Data hazards: forwarding

**Problem:** a RAW (read-after-write) dependency between two nearby
instructions. Without help, the consumer's ID-stage register read would
see a stale value, because the producer's result hasn't been written
back to the register file yet.

**Fix:** `rtl/pipeline/forwarding_unit.sv`, instantiated in the EX
stage. It compares the currently-executing instruction's source
registers (`id_ex`'s `rs1_addr`/`rs2_addr`) against the destination
registers of the instructions one and two stages ahead (`EX/MEM` and
`MEM/WB`), and selects a forwarded value instead of the plain
register-file read when they match:

| Gap (instructions between producer and consumer) | Source of the correct value |
|---|---|
| 0 (immediately following) | `EX/MEM.alu_result` (forwarding_unit `FWD_EX_MEM`) |
| 1 | `MEM/WB`'s already-muxed writeback value (forwarding_unit `FWD_MEM_WB`) |
| 2 | The register file itself, via a write-to-read bypass (see §1.1) |
| 3 or more | The register file's ordinary combinational read (no special handling needed) |

Forwarding feeds **both** ALU inputs, **and** the branch comparison
(`branch_unit`'s `rs1_data`/`rs2_data`), **and** a store's data operand
(`rs2_data` carried into `EX/MEM`) -- all three consume a possibly-stale
operand if forwarding is missed, and `data_hazard_forward.s` (§4) has a
directed assertion for each of them.

### 1.1 Gap 2 needed a fix inside the register file, not the forwarding unit

Gap-2 dependencies (two independent instructions between producer and
consumer) cannot be forwarded from a pipeline register at all: by the
time the consumer reaches EX, the producer has already fully retired
(its `WB` was the *previous* cycle) and no longer exists in `EX/MEM` or
`MEM/WB`. The only place that still has the correct value is the
register file -- but reading it naively hits exactly the same
same-clock-edge race described in `docs/pipeline.md` for Phase 5's
original 2-instruction-gap mistake: the producer's write and the
consumer's `id_ex_reg` capture of its own read both happen via
nonblocking assignment on `posedge clk`, and Verilog resolves that race
to the pre-write value.

This was caught by directed testing, not spotted by inspection: the
first version of `load_use_hazard.s` failed with the loaded address
computed as `0` instead of `0x40`, traced down to `x1` (set 3
instructions earlier -- a gap-2 dependency) reading as its
reset/pre-write value. The fix is `regfile.sv`'s new
`BYPASS_WRITE_TO_READ` parameter: when set, a read whose address matches
the register currently being written returns the write data directly
(a plain combinational address comparison, not reliant on simulator
event-ordering at all). **This defaults to off**, and is only ever
turned on for the pipelined CPU's regfile instance
(`riscv_cpu_pipeline.sv`): turning it on unconditionally would create a
combinational loop in the single-cycle CPU (`riscv_cpu.sv`), where the
same instruction's own read and write are related through that
instruction's own ALU output in the same cycle (e.g. `add x1,x1,x2`) --
see `regfile.sv`'s header comment for the full explanation of why the
two CPUs need different settings of the same parameter.

## 2. Load-use hazard: stalling

**Problem:** forwarding cannot fix a load whose result is needed by the
very next instruction -- `EX/MEM` would only have the load's *address*
computed, not the data memory hasn't been read yet.

**Fix:** `rtl/pipeline/hazard_unit.sv` detects this exact case
(`id_ex_mem_read` -- the instruction currently in EX is a load -- and
its destination register matches the ID-stage instruction's rs1 or
rs2) and asserts three signals for exactly one cycle: `pc_stall` (freeze
the PC), `if_id_stall` (hold the ID-stage instruction another cycle),
and `id_ex_flush` (insert a bubble into EX instead of admitting the
hazardous instruction early). One cycle later, the load has moved into
`MEM/WB`, and `forwarding_unit`'s `FWD_MEM_WB` path supplies the
correct value -- no different from an ordinary gap-1 forward at that
point.

Verified in the waveform (`sim/waveforms/load_use_hazard.vcd`,
generated by `scripts/generate_waveforms.sh`): `dbg_stall` pulses high
for exactly one clock period (10ns, matching the simulation clock) at
each of the three load-use hazards in `load_use_hazard.s` (an ALU
consumer, a store using the loaded value as its data operand, and a
branch condition), confirming the stall is exactly as long as intended
-- not longer (which would cost unnecessary performance) and not
shorter (which would be a correctness bug).

**Documented simplification:** the hazard check compares raw
`rs1`/`rs2` instruction-word fields (extracted positionally for every
instruction by `decoder.sv`, per `docs/riscv.md` §2) without checking
whether the ID-stage instruction's opcode actually treats that field as
a register operand. For LUI/AUIPC/JAL, where that field is really part
of an immediate, a numeric coincidence could trigger an unneeded stall.
This costs a cycle, never correctness, and is the same simplification
most textbook 5-stage designs make -- see `hazard_unit.sv`'s header
comment.

## 3. Control hazards: branch/jump flush

**Problem** (inherited from Phase 5, `docs/pipeline.md`): branch/JAL/JALR
target computation and PC redirect were already correct in EX, but the 2
instructions already fetched from the sequential (now known wrong) path
-- one in `IF/ID`, one about to be captured from `IF` -- were not
discarded, and would incorrectly execute.

**Fix:** the same `hazard_unit.sv` asserts `if_id_flush` and
`id_ex_flush` whenever `ex_redirect_valid` (a taken branch, or any
JAL/JALR) fires. Both `if_id_reg` and `id_ex_reg` gained a `flush` input
that forces their output to an all-zero bubble on the next edge,
regardless of what their data inputs say -- the same "control signals
all zero" bubble convention `docs/pipeline.md` already established for
reset.

Verified in the waveform (`sim/waveforms/control_hazard.vcd`):
`dbg_flush` pulses high for one cycle at each of the 5 control-flow
changes in `control_hazard.s` (the taken `BEQ`, the unconditional `JAL`,
the `JAL` call, and the `JALR` return, plus the program's final `j
test_pass`), and then repeatedly, once per iteration, for the terminal
`done: j done` infinite loop -- every pass through an unconditional jump
needs a flush, even a trivial self-loop, and the waveform shows exactly
that steady-state pattern once the real program logic finishes.

The **not-taken** branch case needs no special handling and asserts
neither signal: `ex_redirect_valid` is false when a branch isn't taken,
so IF simply continues fetching sequentially, exactly as it already did
in Phase 5. `control_hazard.s` includes a not-taken `BNE` specifically
to assert this stays true (see §4).

## 4. Directed test suite

Three test programs under `sim/programs/pipeline_tests/`, using the
same x31 pass/fail convention as Phase 3 (`docs/testing.md`) -- now
usable with real branches/jumps in it, since flush makes them work
correctly through the pipeline:

| File | Covers |
|---|---|
| `data_hazard_forward.s` | Gap-0 (EX/MEM) and gap-1 (MEM/WB) forwarding into the ALU; forwarding into a branch condition |
| `load_use_hazard.s` | The 1-cycle load-use stall, including a load feeding a store's data operand and a load feeding a branch condition directly |
| `control_hazard.s` | Taken-branch flush, not-taken-branch (no flush), unconditional JAL flush, and a JAL-call/JALR-return pair |

Run with:

```bash
make test_hazards
# or directly:
python3 scripts/run_pipeline_hazard_tests.py
```

Like every other phase, this runs under both Icarus Verilog and
Verilator and requires both to agree.

**A verification-methodology bug found and fixed along the way:** the
first version of `tb_pipeline_directed_test.sv` copied Phase 3's
"illegal opcode ever seen" sticky check verbatim. This immediately
failed all 3 tests, on both simulators, with `illegal_opcode_seen` --
not because anything was wrong with the CPU, but because a bubble
(all-zero pipeline-register state, which exists in *every* pipelined
program during fill, every flush, and every stall) decodes to opcode
`0000000`, which is correctly-but-misleadingly flagged `illegal` by
`control_unit.sv`. Phase 3's single-cycle CPU never has bubbles, so this
check was safe there; a pipeline always does, so the check was simply
the wrong tool for this CPU. Fixed by removing it (verification here
relies solely on the x31 convention, same as Phase 5's `tb_pipeline.sv`)
rather than trying to special-case which zero-instructions are "real"
bubbles -- doing that properly would need an explicit `valid` bit
threaded through every pipeline register, which doesn't exist yet.

## 5. Waveforms

```bash
make waves
# or directly:
scripts/generate_waveforms.sh
```

Produces `sim/waveforms/{control_hazard,data_hazard_forward,
load_use_hazard}.vcd`. GTKWave itself needs a display this environment
doesn't have, so these are generated, not screenshotted -- open them
with `gtkwave sim/waveforms/<name>.vcd` on a machine that has one. The
signals worth watching: `dbg_if_instr`/`dbg_id_instr`/`dbg_ex_instr`/
`dbg_mem_instr`/`dbg_wb_instr` (which instruction occupies each stage),
`dbg_stall` (load-use hazard, pulses exactly one cycle per occurrence),
and `dbg_flush` (control hazard, pulses one cycle per taken
branch/JAL/JALR, including the expected steady repeating pattern once
the program reaches its own terminal `j done` loop). The specific
transition timestamps described above (§2, §3) were read directly out
of these generated files, not estimated.
