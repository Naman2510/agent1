## Limits of the method

- Tasks are independent (no task consumes another's output). A dependency graph would constrain which CPU tasks can fill which window; this planner does not model one.
- The gain is bounded by how long the accelerator is busy on its own. The CPU does all operand marshalling for the accelerator, and that dominates accelerator tasks (`scheduler/coschedule/profile_*.csv`: e.g. vecadd N=16 is busy for 16 of its 216 cycles). So streams of small tasks gain little; streams with long-running accelerator operations (matmul) gain the most.
- Plans are computed offline from measured per-task costs, for known streams. They are not a runtime decision.
- One accelerator context: a window can host CPU tasks, not a second accelerator task.
