# Dynamic Runtime Scheduling Report (Phase 15)

Generated by `scheduler/runtime/run_dynamic_scheduler_demo.py` from actual Icarus Verilog simulation of `rtl/cpu/riscv_soc.sv`. All four programs run the SAME fixed 6-workload stream (vecadd N=1,2,4; dot N=1,4; matmul N=2 -- see `scheduler/runtime/gen_dynamic_scheduler_demo.py`); every cycle count below is an end-to-end total for the whole stream, read at the single GPIO sentinel write that fires once all 6 workloads finish. `dynamic_scheduler_demo` is the only one of the four whose engine choice is computed AT RUNTIME by real RV32I instructions (see docs/dynamic_scheduling.md) -- the other three are static baselines for comparison. Correctness of all four is established separately by `sim/testbenches/tb_dynamic_scheduler_correctness.sv` (`make test_dynamic_scheduler_correctness`).

**Headline finding: the dynamic scheduler (492 cycles) is SLOWER than simply always using the accelerator (389 cycles) for this workload stream** -- 103 cycles worse, a real, measured, and honestly reported result, not a bug being explained away. Two real costs combine:

1. **The one known misprediction has a real cost here too.** `vecadd N=2` is dispatched to the CPU (matching the model's Phase 14 misprediction -- see `docs/scheduler_pipeline.md`) when the accelerator would have been faster (61 vs. 50 cycles standalone).
2. **The runtime decision computation itself has a real, non-zero cost.** `dynamic_scheduler_demo` retires 396 instructions and incurs 37 pipeline flushes vs. `oracle_demo`'s 321 instructions and 17 flushes -- every block pays for computing element_count/multiply_count and branching on them, on top of whichever engine it ends up running. For workloads this small (a handful of elements each), that decision overhead is not negligible relative to the work itself.

This is a genuine engineering lesson, not a project failure: **an AI scheduler's own runtime overhead can outweigh the benefit of its decisions when workloads are small enough and its decisions aren't perfect.** A scheduler that is only ever right (`oracle_demo`, 379 cycles) still beats always-accelerator (389 cycles) by 10 cycles -- so the idea has real value here; it is the combination of decision overhead AND one wrong call that erases it in this specific stream. See docs/dynamic_scheduling.md for what this does and doesn't imply.
